# Building and testing an OBS Studio plugin

Hard-won recipe from building `obs-datetime-source` (a FreeType2-based text
source). Covers the whole loop: get `libobs` headers+lib without building the
full OBS app, build the plugin against them, and actually see it render in a
real OBS Studio. Skip straight to the OS-specific section you need.

## The core strategy (do this, not the "obvious" thing)

**Don't build the full OBS Studio UI just to test a plugin.** It's tempting,
but a plugins-disabled OBS frontend build hits a cascade of upstream `throw`s
that assume at least one bundled plugin exists (missing service, missing
video encoder, missing audio encoder — see "Dead end" below). Chasing those
is a time sink unrelated to your plugin's correctness.

Instead:
1. Build a **headless, minimal `libobs`** (UI/browser/scripting/plugins all
   OFF) purely to get headers + an import lib to link against.
2. Build the plugin against that.
3. Install the plugin's output into a **real, fully-installed OBS Studio app**
   (official installer/package — already has its bundled plugins, so none of
   the cascading-throw problems apply) and test there.
4. If possible, match the `libobs` build's version/tag to the real app's
   installed version (Help → About) to minimize ABI drift risk.

## Plugin CMakeLists.txt pattern

Key points baked into a working `CMakeLists.txt` (see this repo's
`plugins/obs-datetime-source/CMakeLists.txt` for the full version):

- Accept `-DLIBOBS_INCLUDE_DIR` / `-DLIBOBS_LIB` to point at an out-of-tree
  obs-studio checkout when `find_package(libobs)` doesn't find an installed
  package config.
- **`obsconfig.h` is generated by OBS's own CMake configure step**, and lands
  in the *build* tree (`<build>/config/obsconfig.h`), not the `libobs/`
  source dir. Add it as a second include dir. Its location relative to
  `LIBOBS_LIB` differs by generator (see path table below) — expose a
  `-DLIBOBS_CONFIG_INCLUDE_DIR` override rather than hardcoding the relative
  `..` count.
- **Strip build-time rpath** (`set(CMAKE_SKIP_BUILD_RPATH TRUE)` +
  `CMAKE_SKIP_INSTALL_RPATH TRUE)`). The plugin is `dlopen()`'d by a host OBS
  process that already loaded its own `libobs` by soname; baking in an
  absolute rpath to whatever `libobs.so` you happened to link against at
  build time risks mapping a second, ABI-mismatched copy into the host
  process instead of resolving against the one already running. (No Windows
  equivalent needed — Windows resolves imports by DLL name against what's
  already loaded in the process.)
- **On Windows, a `SHARED IMPORTED` target needs both `IMPORTED_IMPLIB`
  (the `.lib`) and `IMPORTED_LOCATION` (the `.dll`)** — passing the `.lib`
  for both (fine on Linux, where there's no such split) triggers CMake
  policy CMP0111 warnings and is semantically wrong. Branch on `WIN32`.
- Guard fontconfig (`find_package(PkgConfig)` + `pkg_check_modules`) behind
  `if(UNIX AND NOT APPLE)` — it's Linux-only; Windows/macOS need a different
  font-resolution strategy (see below).

### Artifact path table (what `-DLIBOBS_LIB` / `-DLIBOBS_CONFIG_INCLUDE_DIR` should point at)

| Generator | `libobs` lib | `obsconfig.h` |
|---|---|---|
| Ninja/Makefiles (Linux, single-config) | `<build>/libobs/libobs.so` | `<build>/config/obsconfig.h` (one `..` up from the lib's dir) |
| Visual Studio (Windows, multi-config) | `<build>\libobs\RelWithDebInfo\obs.lib` | `<build>\config\obsconfig.h` (**two** levels up — the per-config subdir adds one) |

Don't trust an auto-computed relative path across generators; always allow an
explicit override and print what you're using.

## Font rendering

FreeType2 rasterizes glyphs into an RGBA texture (upload via
`gs_texture_create`); this part is identical cross-platform. Resolving a
*font family name* to an actual font *file* is not:

- **Linux**: fontconfig (`FcFontMatch`) — works well, no bundled fonts needed.
- **Windows/macOS**: no fontconfig. Either bundle a font file, or (stopgap)
  hardcode a couple of common system font paths
  (`C:\Windows\Fonts\arial.ttf`, `/System/Library/Fonts/Supplemental/Arial.ttf`)
  as a fallback until DirectWrite/CoreText lookup is implemented.

## Color packing convention

libobs color properties (`obs_properties_add_color_alpha`) round-trip through
`obs_data_set_default_int`/`obs_data_get_int` as a packed `uint32_t` matching
`vec4_from_rgba`: **R in the low byte, A in the high byte** (i.e.
`0xAABBGGRR` as a hex literal). Unpack with:
```cpp
r = (val & 0xFF) / 255.0f;
g = ((val >> 8) & 0xFF) / 255.0f;
b = ((val >> 16) & 0xFF) / 255.0f;
a = ((val >> 24) & 0xFF) / 255.0f;
```
Get this backwards and the color picker in the OBS UI won't match what
renders.

## Linux: headless libobs build

```sh
sudo apt install -y build-essential cmake ninja-build pkg-config git \
    extra-cmake-modules uthash-dev libjansson-dev libxkbcommon-dev \
    libgl1-mesa-dev libglvnd-dev libdrm-dev libsimde-dev \
    libfreetype-dev libfontconfig-dev   # last two are for the plugin itself

git clone --recursive https://github.com/obsproject/obs-studio.git ~/obs-studio
cd ~/obs-studio
cmake -B build -G Ninja \
    -DCMAKE_BUILD_TYPE=RelWithDebInfo \
    -DENABLE_FRONTEND=OFF -DENABLE_BROWSER=OFF \
    -DENABLE_SCRIPTING=OFF -DENABLE_PLUGINS=OFF
cmake --build build -j $(( $(nproc) > 1 ? $(nproc) - 1 : 1 ))
```

Notes:
- If `libsimde-dev` isn't packaged on your distro/version, vendor it instead:
  `git clone --depth 1 https://github.com/simd-everywhere/simde.git` and pass
  `-DSIMDe_INCLUDE_DIR=<path>`.
- **`ENABLE_UI` vs `ENABLE_FRONTEND`**: this flag was renamed at some point.
  If your checked-out version rejects one, try the other, or check what's
  actually defined: `cmake -B build -LH 2>/dev/null | grep -i -B2 "qt\|^ENABLE_\|frontend\|UI"`.
- `cmake --build build --target obs` may fail with "unknown target" —
  the libobs CMake target isn't necessarily literally named `obs` across
  versions. With everything else disabled, just build the default target
  (omit `--target`).
- Expect several rounds of "Could NOT find X" during configure
  (ECM/extra-cmake-modules, SIMDe, uthash, jansson, xkbcommon, OpenGL,
  libdrm were all hit in practice) — each is a normal apt package, add and
  re-run configure.
- **AJA/DeckLink/VLC and other vendor-SDK plugins**: don't disable these one
  by one with `-DENABLE_AJA=OFF` etc. — just set `-DENABLE_PLUGINS=OFF`
  up front, which skips the entire `plugins/` subtree (you don't need any of
  OBS's bundled encoders/capture sources just to get `libobs` headers+lib).

Then build the plugin itself:
```sh
cmake -B build -G Ninja \
    -DLIBOBS_INCLUDE_DIR=~/obs-studio/libobs \
    -DLIBOBS_LIB=~/obs-studio/build/libobs/libobs.so
cmake --build build
```

### Linux plugin install location

```
~/.config/obs-studio/plugins/<plugin-name>/bin/64bit/<plugin-name>.so
~/.config/obs-studio/plugins/<plugin-name>/data/...
```

## Windows: headless libobs build

Visual Studio + CMake + Git, no vcpkg needed for OBS itself — **obs-studio's
own CMake auto-bootstraps prebuilt Qt6/obs-deps on Windows**; don't pass your
own `-DCMAKE_TOOLCHAIN_FILE=vcpkg` to *this* configure step, it can interfere
with that mechanism (observed: broke SIMDe path resolution).

```powershell
winget install --id Git.Git -e
winget install --id Kitware.CMake -e
winget install --id Microsoft.VisualStudio.2022.Community -e `
    --override "--add Microsoft.VisualStudio.Workload.NativeDesktop --includeRecommended"
# IMPORTANT: fully close and reopen the terminal after installs so PATH updates apply —
# a stale PATH in an already-open shell is a very common false "not found" here.

git clone --recursive https://github.com/obsproject/obs-studio.git C:\obs-studio
cd C:\obs-studio
git checkout <tag matching your target OBS install's version, e.g. 32.2.2>
cmake -B build_x64 -G "Visual Studio 17 2022" -A x64 `
    -DENABLE_FRONTEND=OFF -DENABLE_BROWSER=OFF `
    -DENABLE_SCRIPTING=OFF -DENABLE_PLUGINS=OFF
cmake --build build_x64 --config RelWithDebInfo
```

(Try `-DENABLE_UI=OFF` instead of `-DENABLE_FRONTEND=OFF` if that's rejected
— same rename caveat as Linux.) `cmake --build ... --target obs` will also
fail here with `MSB1009: Project file does not exist` — omit `--target`, same
reasoning as Linux.

Artifacts land at:
```
C:\obs-studio\build_x64\libobs\RelWithDebInfo\obs.lib   (and obs.dll)
C:\obs-studio\build_x64\config\obsconfig.h
```

For the plugin's own dependencies (e.g. FreeType), use vcpkg — **prefer a
static triplet** so you don't have to chase and copy transitive runtime DLLs
(zlib, libpng, bzip2...) next to the plugin at install time:
```powershell
git clone https://github.com/microsoft/vcpkg C:\vcpkg
C:\vcpkg\bootstrap-vcpkg.bat
C:\vcpkg\vcpkg install freetype:x64-windows-static
```

Then configure/build the plugin:
```powershell
cmake -B build -G "Visual Studio 17 2022" -A x64 `
    -DCMAKE_TOOLCHAIN_FILE=C:\vcpkg\scripts\buildsystems\vcpkg.cmake `
    -DVCPKG_TARGET_TRIPLET=x64-windows-static `
    -DLIBOBS_INCLUDE_DIR=C:\obs-studio\libobs `
    -DLIBOBS_LIB=C:\obs-studio\build_x64\libobs\RelWithDebInfo\obs.lib `
    -DLIBOBS_CONFIG_INCLUDE_DIR=C:\obs-studio\build_x64\config
cmake --build build --config RelWithDebInfo
```
A `LNK4098` "defaultlib 'LIBCMT' conflicts" warning here (dynamic-CRT plugin
+ static-CRT FreeType) is low-risk and safe to ignore for a plugin that only
crosses the module boundary through OBS's own API (opaque pointers,
`bmalloc`/`bfree`) rather than raw CRT allocations.

### Windows plugin install location — NOT `%APPDATA%`

This is the one that costs the most debugging time: on Windows, OBS's
"legacy" third-party plugin scan path uses **`%ProgramData%`**
(`GetProgramDataPath`), not `%APPDATA%` like the Linux/macOS branches do
(`GetAppConfigPath`). Dropping a plugin in `%APPDATA%\obs-studio\plugins\...`
on Windows will silently never be scanned — no error, no log line, nothing.

```powershell
$pluginDir = "$env:ProgramData\obs-studio\plugins\<plugin-name>"
New-Item -ItemType Directory -Force -Path "$pluginDir\bin\64bit" | Out-Null
New-Item -ItemType Directory -Force -Path "$pluginDir\data" | Out-Null
Copy-Item <build output>\<plugin-name>.dll "$pluginDir\bin\64bit\"
Copy-Item -Recurse -Force <repo>\data\* "$pluginDir\data\"
```
Then fully quit and relaunch the real OBS app. Check **Sources → +** for
your source's display name. If it's missing, check Help → Log Files → View
Current Log for the plugin's filename or `obs_module_load` message — no
mention at all almost always means "wrong install path", not a build issue.

### macOS plugin install location (untested, from source inspection only)

```
~/Library/Application Support/obs-studio/plugins/<plugin-name>.plugin/Contents/MacOS/<plugin-name>
~/Library/Application Support/obs-studio/plugins/<plugin-name>.plugin/Contents/Resources/...
```

## Dead end to avoid: running a plugins-disabled frontend headlessly

If you're tempted to also build the full OBS UI (`ENABLE_FRONTEND=ON`) with
everything else off, to get a screenshot without a real OBS install: it
mostly works, but you'll hit a chain of **upstream `throw`s that assume at
least one bundled plugin exists**, each requiring its own local source patch
to survive (a plugins-disabled build has no core module, no streaming
service, no audio/video encoder):

- `SetCoreModuleNames()` throws `"SAFE_MODULES is empty"` when no bundled
  plugin populated the `SAFE_MODULES` compile-time macro.
- `OBSApp::checkForUncleanShutdown()` shows a blocking `QMessageBox` (no CLI
  flag skips it) any time a prior run didn't exit cleanly — which a caught
  `throw` output looks like from the outside.
- `OBSBasic::OBSInit()` throws `"Failed to initialize service"` when no
  service plugin registers `rtmp_common`.
- `SimpleOutput::SimpleOutput()` throws when it can't create an audio
  streaming encoder (no `obs_x264`/`ffmpeg_aac` available) — this one's
  inside a constructor, so patching around it risks a half-constructed
  object causing a more confusing failure later.

None of this reflects on your plugin's correctness — it's purely an artifact
of stripping OBS down to just `libobs`. Getting a real screenshot this way is
possible (each `throw` can be turned into a logged warning as a *local,
never-shipped* test-harness patch) but has sharply diminishing returns.
**Prefer installing into a real, fully-featured OBS install instead** — it
already has every bundled plugin, so none of this fires.

If you do go this route anyway (e.g. for CI screenshot testing), useful
tools: `Xvfb :99 -screen 0 1280x720x24`, `DISPLAY=:99 import -window root
shot.png` (ImageMagick) for screenshots, `xdotool mousemove <x> <y> click 1`
to dismiss modals (screenshot first to find real button coordinates — they
shift a few px between runs).

## Shell gotcha: `pkill -f` can kill your own shell

`pkill -f PATTERN` matches against full command lines. If you're running
inside a wrapper that puts your literal command text into its own process's
argv (common in agent/CI sandboxes — check with `ps aux` if a shell session
mysteriously "resets"), a pattern that appears in the pkill invocation itself
(e.g. `pkill -9 -f "bin/obs"` when your *own* shell's argv contains that
exact substring somewhere) can match and kill an ancestor of the current
shell, not just the target process. Symptom: a multi-line command silently
stops executing partway through, with no error. Fix: match on exact process
name instead of a substring of the full command line —
`pkill -9 -x obs` / `pgrep -x obs` — which doesn't have this self-matching
risk since the pkill/bash processes aren't literally named `obs`.

Related: a `pkill`/`grep` that legitimately finds nothing exits nonzero; if
that's mid-script and not the last command, make sure it can't abort the
rest (`pkill ... || true`) before chaining more commands after it.
